# Wiiをスマートリモコンにする研究 — 成功したこと、できなかったこと

**2026年10月24〜27日の調査記録。** Nintendo Wiiの純正有線センサーバーを、パナソニック照明用の赤外線送信器として再利用するプロジェクト。

## 実際にできたこと

- **緑色起動**で、Wiiリモコンによる照明のON/OFFに成功。
- 時刻スケジュールによる照明のON/OFFに成功。
- Google Homeクラウド連携経由の照明操作に成功（一部応答不良の報告があり、安定性・24時間連続運用は未実証）。
- 別の実験用Starletプログラムによる赤外線送信にも成功したが、これは**純正IOSが動いたまま黄色待機中に送信できたことを意味しない**。

## なぜ黄色待機に移行できなかったか

1. **純正IOSにセンサーバー用の正規STMコマンドが見つからなかった。** 所有機のIOS58/IOS80をRAM上で静的解析。STMの16ビットIOCTL全**65,536値**を検査し、13種類のみが認識され、残り**65,523値**は既定経路へ進んだ。実際のSTMにある権限付きレジスタ書き込み39か所を調べても、GPIO bit8への公開経路は確認できなかった。これは「他の全経路が絶対に不可能」という証明ではない。→ [詳細](docs/03-ios58-ios80-stm-negative-result.md)
2. **待機中のセンサーバー給電そのものが未確定。** 既存の基板資料にはセンサーバー負極側がトランジスタで遮断される構造があり、「暗い」だけでは正極側の給電停止は確定しない。対象基板の黄色待機中の電圧は測定していない。→ [詳細](docs/06-sensorbar-rail-and-carrier.md)
3. **Starletに独自コードを常駐させる正規の簡単な経路がない。** カーネルsyscall 0x56はSTMプロセスを要求し、native module起動にも権限制約がある。→ [詳細](docs/03-ios58-ios80-stm-negative-result.md)
4. **WiiConnect24は任意のGoogle Home HTTPリスナーではない。** CHANSはメール処理などを実行するが、任意のIR GPIO制御・秒単位の受信を保証しない。→ [詳細](docs/04-wc24-and-wakeup.md)
5. **38kHzタイミングの実機検証ができていない。** タイマーの理論分解能と、負荷のあるIOS環境で約13µsごとにGPIOを駆動できるかは別問題。→ [詳細](docs/06-sensorbar-rail-and-carrier.md)

## 緑色起動なら省電力化できるか？

緑色なら必要な照明機能は既に動作している。しかし、**処理をイベント待ちに変えても、BroadwayのCPUが自動的にDoze/Napへ入るわけではない**。

古いlibogcの `idle_func` も、現行libogc/Tuxedoの `KThreadIdleMain` も、待機スレッドが無限ループする。最新のlibogcではDPMクロックゲーティングを初期化するが、Doze/Napは別の機構であり、安全な割り込み復帰制御が必要。具体的なW数の削減効果は今回のWiiでは未計測。→ [詳細](docs/05-green-power-and-libogc-idle.md)

## 結論

- **機能としては成功**：Wiiを赤外線スマートリモコンとして動かせた。
- **黄色待機中の常駐IoT化は未達**：GPIO権限・電気的給電・通信・常駐性・タイミングの5つが独立した壁。
- **緑色常時起動の低消費電力化も未達**：libogcのアイドルCPU処理という具体的な研究対象が見つかった。
- **一般化に注意**：検査対象は特定のIOS58 rev6176 / IOS80 rev6944であり、ほかのIOSや改造版の不可能性は証明していない。
